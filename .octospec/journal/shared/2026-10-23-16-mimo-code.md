# Issue 16：MiMo Code ACP 实施与验证

日期：2026-10-23（Asia/Shanghai）。初始基线 `445d2bb24f6ffc27bb4414c835e6a0b365f9f25b`，分支 `codex/issue-16-mimo-code`；本次提交用于发起 PR。macOS arm64、Node v24.19.0、pnpm 11.19.0。

## 当前结论

薄适配器、SDK/CLI 装配、发行包依赖与双语文档已实现。**Runtime 接入与 MiMo 版本生产兼容性分别评审；最终真实兼容性验收没有通过**。2026-10-24 用户明确接受以下问题作为已披露的上游限制，要求继续评审 Runtime 接入 PR #127：

1. 已安装 MiMo 0.1.15 的 ACP 会先返回 prompt end_turn，再转发末尾正文。共享 ACP 遵守响应完成边界，实际正文因此被截断。须在上游修正完成与更新的顺序；不能用静默时间猜测完整性。

此前使用两个测试 Bot 发起私聊是验收身份选择错误，不应作为用户私聊的阻塞。用户指定使用浏览器中已登录的人类账号，正确私聊已触发真实 Gateway 并收到回复，正文仍有上游截断。

用户先前要求在真实复验通过后合并。2026-10-24 用户进一步明确接受上游已知限制，要求文档区分 Runtime 接入交付与 MiMo 版本生产兼容性。PR #127 按标准 ACP 接入、装配、打包、自动化回归和准确限制说明评审；MiMo 0.1.15 不因此获得生产兼容性结论。要求完整输出的场景不得使用该版本；上游修复后仍须针对具体版本完成真实 SDK、CLI 和 Gateway 精确正文复验。本轮仅更新文档与 PR，不自动合并或关闭 issue；GitHub 审批及 CI 保护继续适用。

## 实施

新增 `octo-runtime-adapter-mimo-code`，默认 `mimoCodeAdapter`，工厂 `createMimoCodeAdapter`，直接复用共享 ACP 并启动 `mimo acp`。工厂沿现有选项允许 executable 覆盖。最终没有自定义 MiMo 客户端，没有修改共享 ACP 或 Gateway 的执行行为，没有安装程序、修改 Provider 配置、读凭据文件或引入历史缓存。

Context v3、每轮独立环境、session/new/load、模型 setter、canonical 流、权限桥、取消和清理均沿共享 ACP。SDK 内部 worker 原生注册；CLI 默认 manifest 注册，根包和 CLI 声明 workspace 依赖，发行包校验覆盖 MiMo 导入及全部 14 个 Adapter。思考强度映射为 null，沿现有未应用提示。默认 Provider 选择优先级不变。

配置名：SDK/CLI Context payload.type 与 Gateway bots[].adapter.adapter_type 都是 `mimo-code`。程序为 `mimo`，命令为 `mimo acp`，不存在 `mimoi` 别名。最初仅执行环境 PATH 未找到程序；后续定位 `~/.mimocode/bin/mimo`，--version=0.1.15，acp --help 正常。不是 MiMo 未安装，也不是 codex 可执行文件缺失。

## 上游缺陷与审查

固定参考 [v0.1.15 ACP 命令](https://github.com/XiaomiMiMo/MiMo-Code/blob/v0.1.15/packages/opencode/src/cli/cmd/acp.ts)使用 NDJSON stdio 并启动进程内 HTTP 服务；[Agent 实现](https://github.com/XiaomiMiMo/MiMo-Code/blob/v0.1.15/packages/opencode/src/acp/agent.ts)的 prompt 路径等待内部 HTTP 返回后直接返回 end_turn，另一条 SSE 通道仍在转发正文。

首次原生 SDK 验收期望 MIMO_SDK_ca218189，实际只收到 MIMO_SDK_c，并已 run.completed。隔离原始 ACP 记录：4331ms 收到 M，4370ms 收到 IMO，4389ms 收到 end_turn 响应，4389–4394ms 才收到 _W、IRE、_OK。这是有 API Key、真实执行成功后的顺序错误，不是安装或认证失败。

曾实验过 MiMo 局部子类，成功 prompt 后等本 session 连续 50ms 安静、最多 1 秒；实验中 SDK/CLI 与群聊多轮完成。但 code-review 的规范与需求两路都最小复现：响应前 first，响应后 75ms 才发送 -last，客户端在 51ms 返回 first 和 end_turn，仍静默截断。架构规则要求上游错误在协议责任方修复，不允许猜测式补偿。因此已移除该客户端、专属依赖及窗口测试；最终代码恢复标准薄封装。不能仅增大等待值宣称修复。

规范审查还发现 Gateway 验收脚本只等 CLI close，未检查清理退出码，退出码 5 或 SIGKILL 也可能误判通过。已修正为退出码必须为 0、终止信号必须为 null，强杀不能通过。下述实验运行的清理观察不替代最终脚本的再次验收。

## 复验与边界

构建后运行 `node scripts/verify-mimo-code.mjs`，其精确正文断言会暴露当前版本的截断。需要将安装目录加入本次命令的 PATH，不修改其他宿主环境。

Gateway 脚本：`OCTO_CHANNEL_QA_ACCOUNTS=/path/to/qa-accounts.md node scripts/verify-mimo-code-gateway.mjs` 默认只验既有 QA 群，可用 MIMO_GATEWAY_MODE=sdk 或 cli 选择入口。设置 MIMO_GATEWAY_BROWSER_DM=1 后启动隔离的私聊接收服务，按脚本输出的 browserPrompt 从人类浏览器账号发送；脚本只记录真实终止事件，必须另外核对浏览器可见回复和精确正文，不能把 run.completed 当作完整验收通过。所有 Home、工具目录和 Kernel/Extra 均独立，正常清理后删除临时目录。
